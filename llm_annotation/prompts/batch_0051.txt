# DÉFINITIONS DES 9 LABELS

**VERROU_TECH**
- Définition : Obstacle, difficulté, problème technique/scientifique CONCRET à résoudre
- ✅ Exemples valides :
     - "manque de précision des capteurs actuels"
     - "absence de modèle prédictif fiable pour la respiration cellulaire"
     - "instabilité de la nano-émulsion à température ambiante"
     - "difficulté de vectorisation de la perfluorodécaline"
- ❌ NE PAS annoter :
     - "le projet (trop générique)"
     - "problème (vague sans précision)"
     - "défi (sans contexte)"

**METHODE_RD**
- Définition : Approche, méthodologie, démarche scientifique précise
- ✅ Exemples valides :
     - "évaluation ex vivo sur explants de peau humaine"

     - "méthode Monte Carlo"
     - "test in vitro sur kératinocytes"
- ❌ NE PAS annoter :
     - "méthode (sans précision)"
     - "étude (vague)"

**TECHNOLOGIE_RD**
- Définition : Technologie, framework, plateforme ou paradigme technique
- ✅ Exemples valides :

- ❌ NE PAS annoter :
     - "technologie (générique)"
     - "informatique (trop large)"

- ❌ NE PAS annoter :
     - "composant (générique)"
     - "système (trop vague)"

**MATERIAU_SPECIFIQUE**
- Définition : Matériau, substance ou molécule spécifique nommée
- ✅ Exemples valides :

     - "mélatonine"

     - "polymère biosourcé PLA"
- ❌ NE PAS annoter :
     - "matériau (générique)"
     - "produit (vague)"

**DOMAINE_RD**
- Définition : Domaine scientifique, secteur d'application, champ disciplinaire
- ✅ Exemples valides :
     - "cosmétique"
     - "respiration cellulaire"
     - "intelligence artificielle"
     - "dermatologie"
- ❌ NE PAS annoter :
     - "recherche (trop générique)"
     - "science (trop large)"

**RESULTAT_RD**
- Définition : Résultat concret obtenu, performance mesurée, livrable
- ✅ Exemples valides :
     - "augmentation de 30% de l'oxygénation cellulaire"
     - "prototype fonctionnel validé"
     - "brevet déposé EP123456"
- ❌ NE PAS annoter :
     - "résultat (générique)"
     - "succès (vague)"

**OBJECTIF_RD**
- Définition : Objectif, but ou cible visée par le projet
- ✅ Exemples valides :
     - "stimuler la respiration cellulaire"
     - "développer un système autonome"
     - "identifier de nouveaux actifs"
- ❌ NE PAS annoter :
     - "but (générique)"
     - "amélioration (sans précision)"

# RÈGLES STRICTES

1. **N'annote QUE ce qui correspond CLAIREMENT à une catégorie**
2. **NE JAMAIS inventer** d'entités absentes du texte
3. Les positions `start` et `end` doivent être **EXACTES** (positions de caractère dans le chunk)
4. **Préfère ne pas annoter** plutôt que d'annoter incorrectement
5. Les entités doivent être **SPÉCIFIQUES** (pas trop génériques)
6. **Évite les chevauchements** entre entités
7. Vérification : `chunk_text[start:end] == entity_text` doit être VRAI

### CHUNK_ID: projet_11__chunk_000011_sub00
```
[SECTION : Mise en oeuvre d’une approche basée sur le “Structured Chain of Thought (ScoT)” adapté à la génération de tests unitaires : SCoT4UT]
Pour mettre en œuvre une stratégie de prompting inspirée de SCoT dans le cadre spécifique de la génération de tests unitaires, nous avons été confrontés à une première difficulté majeure : la méthode SCoT classique repose sur l’identification de blocs élémentaires de raisonnement (boucles, conditions, séquences) adaptés à la génération algorithmique, alors que la rédaction de tests unitaires obéit à une logique différente, centrée sur la validation du comportement attendu d’une méthode.

Afin de dépasser cette limite, nous avons proposé de définir des blocs séquentiels spécifiques à la tâche de test, fondés sur la méthode Arrange-Act-Assert (AAA). Cette formalisation permet de décrire la rédaction d’un test unitaire comme une suite structurée d’étapes de raisonnement en langage naturel, directement interprétables par un modèle de langage. L’approche repose ainsi sur la formalisation d’une chaîne de raisonnement structurée selon le modèle AAA (les détails sont présentés enAnnexe 1.6.2.1.2.1. ).

La mise en œuvre d’une stratégie de prompting inspirée de SCoT pour la génération de tests unitaires implique de disposer de trois types d’informations :

des méthodes à tester accompagnées du contexte approprié ;

des tests unitaires rédigés pour ces méthodes ;

des explications en langage naturel, étape par étape, décrivant la manière dont ces tests ont été construits, rédigées selon le modèle AAA (ce que nous appelons des SCoT AAA).
```

### CHUNK_ID: projet_11__chunk_000044_sub00
```
[SECTION : Modèle : AthenaTest]
Architecture

Modèle basé sur l’architecture du modèle BART. BART est un « denoising autoencoder » qu’utilise le standard architecture Transformers « sequence-to-sequence » en substituant des fonctions d’activation ReLU par des GeLU. Le pré entrainement s’effectué sur l’architecture large du modèle composé de 12 couches encoder et 12 couches decoder. Le modèle a été entrainé en précision mixte, en utilisant la procédure d’optimisation stochastique Adam avec paramètres d’optimisation et , . Ils ont utilisé un « scheduler inverse root learning rate » avec un learning rate de base de 0.0001 et une période de « warmup » de 5000 « update steps » et accumulation local du gradient avec une fréquence de 4 « update steps ».

Pré entrainement

Le modèle a été entrainé sur la BDD METHOD2TEST. Le pré entrainement du modèle s’est fait en corrompant des documents (token masking, token deletion, remplissage et permutation d’instructions) et en optimisant la fonction de perte entropie croisée entre la sortie du decoder et la séquence d’entrée originale.

Le pré entrainement s’est fait dans deux étapes : pré entrainement en anglais où le modèle est pré entrainé sur un large corpus de texte en anglais et Code pré entrainement où le modèle est pré entrainé sur du code source en Java. Le pré entrainement c’est fait de façon semi-supervisé.

RQ1 : Est-ce que le pré entrainement du modèle a un impact sur les performances de la génération de tests unitaires ?

Les auteurs ont testé cinq niveaux de pré entrainement avec la même architecture e, changeant les données de pré entrainement :

Scratch model : pois initialisés de façon aléatoire ;

Anglais : Pré entrainement avec un corpus volumineux de texte en anglais ;

Java code : Pré entrainement avec un corpus volumineux de code en Java ;

Anglais + Java : Pré entrainement avec les deux jeux de données (anglais et code Java)

Le finetuning a été fait avec seulement avecle minimum de focal context (le focal method et le test case) car l’objectif a été d’évaluer l’impact du pré entrainement
```
