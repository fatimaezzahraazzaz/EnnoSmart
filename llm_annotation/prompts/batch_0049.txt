# DÉFINITIONS DES 9 LABELS

**VERROU_TECH**
- Définition : Obstacle, difficulté, problème technique/scientifique CONCRET à résoudre
- ✅ Exemples valides :
     - "manque de précision des capteurs actuels"
     - "absence de modèle prédictif fiable pour la respiration cellulaire"
     - "instabilité de la nano-émulsion à température ambiante"
     - "difficulté de vectorisation de la perfluorodécaline"
- ❌ NE PAS annoter :
     - "le projet (trop générique)"
     - "problème (vague sans précision)"
     - "défi (sans contexte)"

**METHODE_RD**
- Définition : Approche, méthodologie, démarche scientifique précise
- ✅ Exemples valides :
     - "évaluation ex vivo sur explants de peau humaine"
     - "analyse par cytométrie en flux"
     - "méthode Monte Carlo"
     - "test in vitro sur kératinocytes"
- ❌ NE PAS annoter :
     - "méthode (sans précision)"
     - "étude (vague)"

**TECHNOLOGIE_RD**
- Définition : Technologie, framework, plateforme ou paradigme technique
- ✅ Exemples valides :
     - "nano-émulsion"
     - "deep learning"
     - "spectroscopie Raman"
     - "encapsulation liposomale"
- ❌ NE PAS annoter :
     - "technologie (générique)"
     - "informatique (trop large)"

**EQUIPEMENT_RD**
- Définition : Équipement physique, machine, instrument utilisé
- ✅ Exemples valides :
     - "microscope à fluorescence"
     - "cytomètre en flux"
     - "spectromètre de masse"
     - "banc d'essai thermique"
- ❌ NE PAS annoter :
     - "machine (générique)"
     - "ordinateur (sans spec)"

**COMPOSANT_TECHNIQUE**
- Définition : Composant, élément technique d'un système ou produit
- ✅ Exemples valides :
     - "vectorisateur lipidique"
     - "capteur infrarouge"
     - "algorithme de tri"
     - "complexe oxygénant"
- ❌ NE PAS annoter :
     - "composant (générique)"
     - "système (trop vague)"

**MATERIAU_SPECIFIQUE**
- Définition : Matériau, substance ou molécule spécifique nommée
- ✅ Exemples valides :

- ❌ NE PAS annoter :
     - "matériau (générique)"
     - "produit (vague)"

**DOMAINE_RD**
- Définition : Domaine scientifique, secteur d'application, champ disciplinaire
- ✅ Exemples valides :
     - "cosmétique"
     - "respiration cellulaire"
     - "intelligence artificielle"
     - "dermatologie"
- ❌ NE PAS annoter :
     - "recherche (trop générique)"
     - "science (trop large)"

**RESULTAT_RD**
- Définition : Résultat concret obtenu, performance mesurée, livrable
- ✅ Exemples valides :
     - "augmentation de 30% de l'oxygénation cellulaire"
     - "prototype fonctionnel validé"
     - "brevet déposé EP123456"
- ❌ NE PAS annoter :
     - "résultat (générique)"
     - "succès (vague)"

**OBJECTIF_RD**
- Définition : Objectif, but ou cible visée par le projet
- ✅ Exemples valides :

     - "identifier de nouveaux actifs"
- ❌ NE PAS annoter :
     - "but (générique)"

# RÈGLES STRICTES

1. **N'annote QUE ce qui correspond CLAIREMENT à une catégorie**
2. **NE JAMAIS inventer** d'entités absentes du texte
3. Les positions `start` et `end` doivent être **EXACTES** (positions de caractère dans le chunk)
4. **Préfère ne pas annoter** plutôt que d'annoter incorrectement
5. Les entités doivent être **SPÉCIFIQUES** (pas trop génériques)
6. **Évite les chevauchements** entre entités
7. Vérification : `chunk_text[start:end] == entity_text` doit être VRAI

```
[SECTION : A3Test : Assertion-Augmented Automated Test Case Generation]
Limites d’AnthenaTest :

Manque de consistance de noms et de vérification de signature de test.

L’approche profite des principes d’adaptation de domaine où le but est d’adapter les connaissances existantes en partant d’une tâche de génération d’assertion pour l’adapter après sur la tâche de génération de cas de tests.

Après le modèle pré-entrainé est fine-tuné pour la génération de cas de tests où l’objectif est d’apprendre les relations entre la méthode focale (focal method) et le cas de test correspondant.

Pour chaque cas de test généré ils utilisent une approche de vérification pour la consistance du nom et les signatures des tests.

Ils ont évalué leur modèle sur la BDD Defects4J

RQ1 : De combien est plus effective A3Test comparé avec AnthenaTest ?

A3Test atteint 147% plus de cas de tests corrects (correctness) et 15% plus de couverture de méthodes (method coverage) avec moins de cas de tests générés que AnthenaTest

RQ2 : A3Test performe mieux que les modèles pré-entrainés existants ?
```

```
[SECTION : Première partie : Génération de Chaînes de raisonnement structurées selon le modèle AAA par LLM (SCoT AAA)]
Dans cette première étape, l’objectif est de générer des chaînes de raisonnement structurées selon le modèle Arrange-Act-Assert (AAA) pour une méthode à tester (MaT) à l’aide d’un LLM.

Pour les points (a) et (b) ci-dessus, nous nous appuyons sur la base de données methods2test (Tufano et al.), appliquée initialement pour le fine-tuning du modèle ATHENATEST. Cette base contient des couples « méthode à tester, test unitaire rédigé par un humain », assortis de certains éléments de contexte, mais sans les projets complets dont ces méthodes sont issues.

Pour le point (c), nous avons proposé de générer les explications étape par étape à l’aide d’un LLM pour un échantillon de methods2test. Nous avons, dans un premier temps, rédigé « à la main » des SCoT AAA pour une dizaine de méthodes choisies aléatoirement, en décrivant en langage naturel, selon le modèle AAA, les étapes de rédaction de leurs tests unitaires (ce que nous appelons SCoT AAA). Ces exemples enrichis (MaT, TU, SCoT AAA) ont servi à configurer un premier prompt few-shots, permettant de générer automatiquement des SCoT AAA pour un échantillon plus large de la base methods2test.

À partir de là, nous avons constitué une nouvelle base au format <Méthode à tester, SCoT AAA, test unitaire>. Nous avons ensuite sélectionné aléatoirement un sous-ensemble de ces exemples enrichis et construit un second prompt few-shots ne contenant plus que les couples <MaT, SCoT AAA>. Ce prompt est appliqué pour soumettre au LLM de nouvelles méthodes à tester et lui demander de générer, pour chacune, le SCoT AAA correspondant.

Le recours à un échantillonnage aléatoire répond à deux objectifs :

éviter un biais excessif lié au choix initial des exemples pour lesquels les SCoT AAA ont été rédigés manuellement, en introduisant une variabilité qui « dilue » cet effet ;

tenir compte des observations de Li et al., qui suggèrent que le choix des exemples few-shots peut influencer significativement le comportement du modèle.
```

```
[SECTION : Using Large Language Models to Generate JUnit Tests: An empirical Study]
Actuellement il n’est pas clair quelle est l’effectivité de l’utilisation de modèles pré-entrainés en génération de code avec prompt pour générer cas de tests unitaires dans un langage de programmation fortement typé comme Java.

Des études ont montré des meilleurs résultats pour l’utilisation de ces modèles pour la génération de cas de tests unitaires dans des langages de programmation moins typés comme python ou javascript.

Les auteurs ont fait une étude empirique pour comparer des modèles LLMs : Codex, GPT-3.5-Turbo et StartCoder pour générer des tests unitaires pour des classes dans la version Java du dataset HumanEval et 47 projets « open-source » dans le dataset SF110.

Questions de recherche :

RQ1 : Dans quelle mesure les LLM peuvent générer des tests JUnit

L’évaluation des tests générés a été faite en fonction de leurs taux de compilation, de leur exactitude, de la couverture du code et de leur qualité (en termes d’ «unit test smells »).

Les tests générés ont été examinés non seulement en termes de leur exactitude, mais aussi de leur qualité, ainsi que de l'efficacité de différents styles de contexte.

Unit Test smells : sont des indicateurs de problèmes potentiels, d'inefficacités ou de mauvaises pratiques de programmation/conception dans une suite de tests unitaires, allant des tests trop lents/fragiles aux tests trop complexes ou trop étroitement couplés à l'implémentation du code testé.

D’autres travails concurrents ont étudié l’utilité des LLMs comme une aide pour des techniques de génération de tests basées sur « search-based » sur des langages de programmation peu typés. Le travail des auteurs ont étudié si les LLMs peuvent être utilisés sur étager pour générer des tests unitaires pour un langage comme Java. Ils évaluent les tests générés en termes de correctness mais aussi sa qualité et l’efficacité des différents styles de contexte.
```
